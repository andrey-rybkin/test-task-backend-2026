# Синхронизация amoCRM → PostgreSQL

[![PostgreSQL tests](https://github.com/andrey-rybkin/test-task-backend-2026/actions/workflows/tests.yml/badge.svg)](https://github.com/andrey-rybkin/test-task-backend-2026/actions/workflows/tests.yml)

## Краткий отчёт о решении

Синхронизация раньше искала и обновляла JSONB по одной записи, из-за чего росло число обращений к БД, а частично загруженный CRM-снимок мог привести к некорректной очистке. Мы сохранили точку входа `collect_leads_customers(is_full=True)`, но изменили способ хранения и применения данных.

Покупатели, сделки, контакты и компании теперь хранятся отдельными строками в нормализованных таблицах; исходный CRM JSON сохраняется в поле `data`. Индексируемые CRM ID и логины позволяют сопоставлять записи без загрузки всех JSON в Python. Совпадение по логину используется только при однозначном результате. Если сделка уже связана с одним агрегатом, а покупатель найден в другом, сохраняется агрегат сделки, туда переносятся связанные данные и `send_methods`, после чего записывается текущая версия сделки.

Выгрузка CRM идёт потоком во временную staging-таблицу пакетами по 500 записей. Пока не получены оба полных потока, рабочие таблицы не меняются. Затем пакетные upsert, merge и очистка выполняются в одной транзакции под advisory lock. Поэтому ошибка выгрузки, включая HTTP 204 посреди пагинации, не запускает удаление данных, а частичный проход вообще не выполняет очистку. Полный проход удаляет отсутствующие записи, сущности с маркером «удалить» в любом регистре и ставшие пустыми агрегаты.

**Что оставлено и почему.** Полный JSON CRM остаётся в `data`: это сохраняет исходные поля и позволяет переживать изменения API без постоянных миграций схемы. Точка входа и формат `general`/`api_value` тоже сохранены для совместимости. Реальные URL, авторизация CRM и обработка секретов не добавлялись: в исходном проекте не было рабочих настроек или учётных данных; их нужно подключить на стороне приложения.

Воспроизводимый прогон **20 тыс. покупателей + 50 тыс. сделок** (payload со строкой 2,5 КБ, без CRM-сети и вложенных контактов/компаний) на PostgreSQL 16 в отдельной схеме: первая загрузка — **34,92 с, 517 SQL, 145 commit**; повтор без изменений — **30,67 с, 437 SQL**; 5% изменённых имён и 1% удалённых сделок — **29,48 с, 434 SQL**. Пик RSS за три прогона — **143,4 МиБ**, размер временной таблицы с индексами — **48,3 МиБ** (PostgreSQL сжимает повторяющиеся строки). Проверка `EXPLAIN (ANALYZE, BUFFERS)` на 20k/50k подтвердила `Index Scan` по точному логину покупателя и названию сделки. Ускорение повторного прогона не обещается: staging и проверка всех JSON выполняются вновь ради безопасной очистки. Время сети и большой объём связей в замер не входят.

## Запуск и миграция

Требуются Python ≥ 3.9, Flask-SQLAlchemy и PostgreSQL. Перед переносом сделайте резервную копию и остановите синхронизацию. Примените `migrations/001_normalize_crm_entities.sql`, переведите внешние запросы со старых JSONB-колонок на модели `AmoCustomer`/`AmoLead`, проверьте данные и полный sync. Только после этого применяйте `migrations/002_drop_legacy_jsonb.sql`: она удаляет старые колонки.

Интеграционные тесты запускаются на PostgreSQL и создают свою временную схему; существующие таблицы они не удаляют:

```sh
TEST_DATABASE_URL='postgresql+psycopg://user:password@127.0.0.1:5432/test_db' \
  python -m unittest discover -s tests -v
```

Покрыты merge, неоднозначный логин, сбой CRM-выгрузки, частичная/полная очистка, покупатель без логина и маркер удаления. Для реального amoCRM API приложению необходимы настроенные URL и авторизация.

Для повторения замера на PostgreSQL (скрипт создаёт и удаляет только свою уникальную схему):

```sh
TEST_DATABASE_URL='postgresql+psycopg://user:password@127.0.0.1:5432/test_db' \
  python tests/bench_sync.py 20000 50000
```

На PostgreSQL пройдены 13 тестов как на Python 3.9, так и на 3.14, включая откат применения, исчезновение связанных сущностей и обе миграции на изолированной старой схеме. Результаты синтетического прогона зависят от машины; **не** сравнивайте секунды разных окружений как одинаковый benchmark.
