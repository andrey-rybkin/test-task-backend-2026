# Синхронизация amoCRM → PostgreSQL

## Краткий отчёт о решении

Синхронизация раньше искала и обновляла JSONB по одной записи, из-за чего росло число обращений к БД, а частично загруженный CRM-снимок мог привести к некорректной очистке. Мы сохранили точку входа `collect_leads_customers(is_full=True)`, но изменили способ хранения и применения данных.

Покупатели, сделки, контакты и компании теперь хранятся отдельными строками в нормализованных таблицах; исходный CRM JSON сохраняется в поле `data`. Индексируемые CRM ID и логины позволяют сопоставлять записи без загрузки всех JSON в Python. Совпадение по логину используется только при однозначном результате. Если сделка уже связана с одним агрегатом, а покупатель найден в другом, сохраняется агрегат сделки, туда переносятся связанные данные и `send_methods`, после чего записывается текущая версия сделки.

Выгрузка CRM идёт потоком во временную staging-таблицу пакетами по 500 записей. Пока не получены оба полных потока, рабочие таблицы не меняются. Затем пакетные upsert, merge и очистка выполняются в одной транзакции под advisory lock. Поэтому ошибка выгрузки не запускает удаление данных, а частичный проход вообще не выполняет очистку. Полный проход удаляет отсутствующие записи, сущности с маркером «удалить» и ставшие пустыми агрегаты.

**Что оставлено и почему.** Полный JSON CRM остаётся в `data`: это сохраняет исходные поля и позволяет переживать изменения API без постоянных миграций схемы. Точка входа и формат `general`/`api_value` тоже сохранены для совместимости. Реальные URL, авторизация CRM и обработка секретов не добавлялись: в исходном проекте не было рабочих настроек или учётных данных; их нужно подключить на стороне приложения.

На синтетическом прогоне **20 тыс. покупателей + 50 тыс. сделок** (payload со строкой 2,5 КБ, без CRM-сети и вложенных контактов/компаний) sync занял **35,65 с**, пиковый RSS составил **127,5 МиБ**, выполнено **517 SQL-команд**. В PostgreSQL сохранено 70 тыс. CRM-записей и 20 тыс. агрегатов. Это один локальный замер на PostgreSQL 16, а не оценка скорости реального CRM API; с контактами и компаниями время и память могут быть выше.

## Запуск и миграция

Требуются Python, Flask-SQLAlchemy и PostgreSQL. Перед переносом сделайте резервную копию и остановите синхронизацию. Примените `migrations/001_normalize_crm_entities.sql`, переведите внешние запросы со старых JSONB-колонок на модели `AmoCustomer`/`AmoLead`, проверьте данные и полный sync. Только после этого применяйте `migrations/002_drop_legacy_jsonb.sql`: она удаляет старые колонки.

Интеграционные тесты запускаются на отдельной временной PostgreSQL-БД:

```sh
TEST_DATABASE_URL='postgresql+psycopg://user:password@127.0.0.1:5432/test_db' \
  python -m unittest discover -s tests -v
```

Покрыты merge, неоднозначный логин, сбой CRM-выгрузки, частичная/полная очистка, покупатель без логина и маркер удаления. Для реального amoCRM API приложению необходимы настроенные URL и авторизация.
